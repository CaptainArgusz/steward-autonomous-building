# Steward — an autonomous operator for the PLATO-40 building

proximata Hackathon '26 · Rhomberg track · "PLATO × CLARA Future — The Autonomous Building"

Steward replays a year of operating data from **PLATO-40**, a fictional 40-room self-check-in
hotel, and acts as its operator: it detects operational problems, decides on prioritised
actions within explicit autonomy rules, records them through a mock executor, and states how
each action would be verified.

> PLATO-40 is a synthetic reference property. Nothing here is a statement about real PLATO
> buildings or about CLARA. All effects of actions are simulated; no savings are measured.

**Status: work in progress.** The three mandatory scenarios (checkout conflict, water leak,
heating vs comfort) have a first working version, the insights report has 12 findings, and
there is a web UI with a replayable Live Day and a real-time 3D floor view. See
[PROJECT.md](PROJECT.md) §12 for results and known issues.

## Run it

Requirements: [uv](https://docs.astral.sh/uv/) (it installs Python 3.12 and all dependencies).

```bash
uv sync
uv run steward run <data_dir> --out decisions.jsonl
```

That one command takes a dataset directory (the folder containing `building.json`, the CSV
files and `events.jsonl`) and writes `decisions.jsonl`. It then validates the file against the
decision contract and prints a summary. It needs no network access and no API key.

```bash
uv run steward run data/quickstart --out out/quickstart/decisions.jsonl   # 21-day set, included
uv run steward run data/dev        --out decisions.jsonl                  # full year → root deliverable
uv run steward run data/holdout/<extracted folder> --out decisions_holdout.jsonl
```

The quickstart dataset is included in this repository. The dev and holdout datasets are not;
[data/README.md](data/README.md) says where to put them.

Web UI (needs Node 20+):

```bash
make ui        # runs the pipeline, writes the data bundles, serves http://localhost:5173
```

### LLM-generated recommendations

Open **Lessons**: recommendations load automatically from the selected dataset, balancing
comfort, reliable operations and maintenance effort. Switching datasets loads its own report;
repeat visits reuse the cached report without another model request.
The existing evidence maps and charts accompany advice generated by Groq. The expanded
proof contains the computed findings and uncertainty. Reports and evidence are saved locally
in `out/recommendations/`.

Set `GROQ_API_KEY` in the repository-root `.env`. `GROQ_MODEL` defaults to
`openai/gpt-oss-120b`. The local Vite server and preview server make the API call on the server.
A static deployment can display exported evidence; generating advice requires that local server.

Lessons computes evidence from the selected dataset. It includes the existing statistical
analyses, broad comfort and sensor-coverage summaries, guest-request counts and postponed
maintenance notes. The model receives observations and uncertainty; the existing authored
recommendation text is excluded. Advice is advisory and benefits are qualitative. Source IDs
and numeric claims are checked against cited observations; semantic interpretations still
require review. Coverage is limited to these analyses and the available records.

For holdout, put the extracted dataset in `data/holdout` or one subdirectory beneath it,
then run `uv run steward ui <extracted-directory>` and select holdout in the UI. The manifest's
profile must identify the dataset. Each report is cached in `out/recommendations/` by dataset
contents, analysis code and model. The operational decisions command stays offline.
The standard `insights.md` submission remains the reproducible statistical report.

Other commands:

```bash
uv run steward validate decisions.jsonl --data-dir data/dev   # contract + building checks
uv run steward score decisions.jsonl --data-dir data/dev      # compare with outcomes the replay recorded
uv run steward insights data/dev                              # regenerate insights.md and insights.jsonl
uv run steward info data/dev                                  # tables, row counts, missing cells
make check                                                    # lint, tests, quickstart run
```

## How it works

```
data dir ─► Dataset ─► detectors ─► Decision[] ─► decisions.jsonl ─► mock executor ─► action trail
```

- **`steward.dataset`** loads one dataset directory. Timestamps become timezone-aware UTC;
  blank fields stay missing and are never read as zero.
- **`steward.detectors`** holds one module per problem class. A detector replays the data in
  time order and may only use information that was available at the decision's timestamp
  (forecast issue time, tariff publication time, booking creation time, when a roster change
  became known).
- S04 compares sustained AHU filter pressure with fan and airflow readings, and treats
  floor-wide missing room sensors as a separate gateway data gap. Service is proposed for
  approval, never assumed completed.
- S05 uses the same room replay and capacity queue as S01 to identify weekend arrival
  shortfalls after a known cleaner absence. It proposes one coordination plan, a request
  for extra capacity and conditional guest updates without counting on-call help in advance.
- Logistics orders an extra waste pickup or vending restock when the trailing use rate (plus,
  for vending, guest-hours already booked) projects a shortfall before the regular service, and
  sends a robot to carry floor bins on days a cleaner is known absent.
- Energy plans the battery for the next day once prices are published and acts only when the plan
  clearly beats the battery's recent routine; every saving is a simulated estimate.
- **`steward.contract`** defines the `Decision` model after `DECISION_CONTRACT.md`. It rejects
  decisions that break the autonomy rules — for example `dispatch_technician` or `block_room`
  without `requires_human_approval`, or guest consent without approval — and derives the
  `autonomy` level from the two flags.
- **`steward.pipeline`** runs all detectors, sorts the result and writes it. Output is
  deterministic: the same data gives a byte-identical file.
- **`steward.executor`** is a mock executor. Autonomous decisions are logged as
  `executed_simulated`; everything else stays `pending_human_approval` (and guest consent).

Only actions from the challenge vocabulary are used. Two extra fields may appear on a
decision: `proposed_message` and `message_language` (a guest message that is proposed, never
delivered).

## Assumptions and limitations

- The data is an offline replay: no action changes later observations, so we cannot observe
  whether an action worked. Each decision instead carries a `verification_plan`.
- Early check-in requests whose answer depends on the morning's cleaning plan get a holding
  reply by their `response_due_utc` (no time promised, says when we confirm), then either a
  confirmation or a realistic time. These replies are filed as `guest_request` episodes, not as
  room incidents. Only requests linked to an operational problem are answered; general requests
  (wifi, towels, ...) are out of scope.
- The mock executor runs actions in dependency order and refuses unsafe ones with a reason:
  `release_room` without a completed cleaning since the last checkout, a robot sent into an
  occupied room, or staff known to be absent. Actions that wait for approval stay pending, and
  steps that depend on them are marked `blocked_by_dependency`.
- There is no ground truth in the participant data. Detection quality is argued from evidence.
- A booking becomes known at `created_utc`. The final `cancelled` status has no timestamp,
  so replay planning does not use it to remove expected arrivals. Overlapping known bookings
  make the arrival uncertain; the planner does not make an automatic promise for that room.
- Roster absences apply when `status_known_utc` arrives. Later meter readings do not rewrite
  an earlier flow calculation.
- A detector that raises an error is logged and skipped so that a run still produces output;
  the command then exits with a non-zero status. `--strict` aborts instead.
